# 视觉/操作框架：漏洞清单与设计思路（2026-10-03 整理）

> 来源：连续两晚的实操（基建排班图 → 会客室/制造站 → 计算器 → README → 公招计算器找水月）。
> 结论先行：**这个"简单任务"其实叠了 6 个难点，而框架里每一个都缺** ✗，所以每一步都在踩新坑。

---

# 第一部分：漏洞清单（按根因层级，不按发现时间）

## 第 0 层：哲学性错误 ——「报成功」被当成了「做成了」

**这是所有问题的放大器，也是最该先修的。**

实测到的"报成功但没生效"（每一条都当场复核过）：

| 工具 | 它报的 | 实测事实 |
|---|---|---|
| `focus_window` | `OK … UNTOP done` | **前台窗口一个字都没变** |
| `input.move` | `true` | **光标没动**（Win32 `GetCursorPos` 一查就差 551px） |
| `input.key` | `true` | Ctrl+F 发给了**别的窗口** |
| `input.type` | `true` | 字打进了**别的程序的输入框** |
| `click` | `已点击 (x,y)` | 可能落在别的窗口/空地方 |
| `find_text` | `找到` | **屏幕任何角落**出现该词就算找到（含聊天记录）→ 假阳性 |
| `windows_list` | "坐标可直接 click" | 底层偏 **1.25 倍** |
| 视觉模型 | "两个槽位都已进驻" | **两个都是空的** |

**后果**：上层**无法知道下层失败了** → 会出现"她做错了却以为成功""我宣布完成而光标根本没到"。

## 第 1 层：坐标系与窗口身份

| # | 漏洞 | 实测现象 |
|---|---|---|
| 1 | **DPI 虚拟化没处理** | PowerShell 拿到的窗口坐标是"物理÷1.25"；底层注释写着要乘回去，代码却没乘；而工具层补乘了一次 → **底层错、工具对**；我修了底层又忘了删工具层那次 → **双乘**（同一个 bug 换个方向再犯） |
| 2 | **同名窗口分不清** | Edge 为**同一个页面**暴露 3+ 个**标题逐字相同**的顶层窗口；按标题/面积挑会挑错 → **只有 hwnd 唯一**（前台 hwnd 才是"当前可见那个"） |
| 3 | **`IsWindowVisible` 当过滤条件** | 浏览器的窗口可能 `visible=false`，**却仍是前台窗口** → 被整个漏掉（我的 `target()` 因此报"找不到窗口"，白跑一轮） |
| 4 | **窗口位置会变** | 我把自己窗口停在 (1180,0) 后就**硬编码**"排除 x>=1175" → 窗口移回左边后规则失效 → **我自己的对话文字被当成页面文字** |
| 5 | **最小化窗口报假矩形** | 最小化时 `GetWindowRect` 返回 `-32000,-32000`，**这个值会被当真** → 照它点击必错 |
| 6 | **"是前台"不等于"没最小化"** | `ensureForeground` 只看前台，于是"前台但最小化"被判为"已就绪" → 截图里只有桌面 |

## 第 2 层：遮挡（最容易被忽略、后果最严重）

| # | 漏洞 | 实测现象 |
|---|---|---|
| 7 | ⭐**截图是"屏幕像素"而不是"窗口像素"** | 被遮挡的部分**根本没有被捕获**；捕获到的是**遮挡者的像素** |
| 8 | ⭐**由 7 派生：按"目标窗口矩形"过滤 OCR 词 → 把遮挡者的文字算到目标头上** | 实测：我的 DSH 对话内容（"水月""阿""温蒂"…）被当成了**页面卡片名** → 差点据此移动鼠标 |
| 9 | **遮挡判断必须看 z 序** | 只看"矩形是否重叠"会把**压在下面的自己**也算成遮挡者（我第一版就错） |
| 10 | **"它是前台所以没被遮挡"这个推断也不成立** | 实测：浏览器是前台，却仍被别的窗口盖住 |
| 11 | **"排除自己窗口"不能硬编码** | 必须**每次动态取**自己所有窗口的矩形 |

## 第 3 层：OCR 与视觉模型的能力边界

### OCR
| # | 漏洞 | 实测现象 |
|---|---|---|
| 12 | **中文被按单字切开** | OCR 给的是"公""招"两个词；**不合并短语就永远匹配不到多字词** |
| 13 | **形近字错误** | 控场→**粹场** / 治疗→**冶疖** / 支援→**相** / 钼铅→**铝铅** / 格雷伊→**格蕾伊** / 珊比→**瑕比** |
| 14 | **词序不保证** | 顺序合并会造出**负宽度**、**反序**短语（"招计算公"） |
| 15 | **假阳性** | "数据目录"四个字在屏幕别处出现也算"找到" |
| 16 | **小字直接崩** | 卡片上的干员名（~15px）几乎读不出来（而视觉模型能读对） |

### 视觉模型
| # | 漏洞 | 实测现象 |
|---|---|---|
| 17 | ⭐**同一屏里两个答案自相矛盾** | 位置声明`水月=2,1`（**正确**）＋名字列表**漏掉水月**（错误）→ 我拿列表否决位置，**把正确答案误杀了** |
| 18 | ⭐**提示词诱发幻觉** | 我在提示词里写"最后写 水月=R,C" → 它在**没有水月**的屏里也填了 `水月=2,1` |
| 19 | **不能给像素坐标** | 同一按钮每次差 20~120px，最多偏 260px |
| 20 | **能给离散答案** | "第几行第几列""是/否""第几号" 明显更可靠 ← **这是可用之处** |

### 实现细节
| # | 漏洞 |
|---|---|
| 21 | `nativeImage.crop()` 要 `{x,y,width,height}`，写成 `w/h` 会报 "conversion failure" |

## 第 4 层：我自己探针的方法论错误（这一晚最耗时的部分）

| # | 漏洞 | 后果 |
|---|---|---|
| 22 | **先截图再聚焦** | 在**错的画面**上做**正确的匹配** |
| 23 | ⭐**按窗口百分比猜区域**（0.32 / 0.48 都猜错） | 8 屏全裁到标签区/页脚；应该用**锚点文字**定位 ROI |
| 24 | **滚动点放错位置** | 滚轮只作用于**光标下**的控件；chips 是**内层可滚动框**，滚页面动不了它 |
| 25 | **锚点选了当时不可见的元素** | 匹配不到 → 误判"页面没有" |
| 26 | **`Start-Sleep` 干等固定时长** | 探针 9 秒跑完，我等 190 秒（21 倍浪费）；应该 `WaitForExit` |
| 27 | **解析把"报告没找到"当成"找到了"** | 正则 `含水月` 命中了字面量 `水月=-1,-1` |

# 第二部分：设计思路

## 地基三原则（缺一条整个系统就不可信）

```
① 每个动作 = 【前提断言】+ 执行 + 【效果断言】；断言失败就是失败，绝不许返回 true
     键鼠动作前：回读 GetForegroundWindow == 目标窗口？（不是就拒绝执行）
     键鼠动作后：回读 GetCursorPos（move/click）/ 前台 / 局部 ROI 帧比对
     定位动作：必须回答"我凭什么相信这是目标"（定位器名 + 置信度）

② "事实"只来自确定性通道
     窗口句柄 · 控件树(UIA) · OCR 词框 · 模板匹配 · 几何约束
     模型只回答【语义】和【离散选择】：是/否、第几号、第几行第几列
     ★ 模型永不产出像素坐标 ★

③ 验证要验证【被指的那个对象本身】，不要比对两份都可能残缺的清单
     例：模型给 (R,C) → 裁出那一格 → 单独问"这张卡是谁" → 才是核对
```

## 遮挡是一等公民（新增）

```
· 每次动态取"我自己所有窗口"的矩形 + z 序（不硬编码！）
· 截图后：对每个待识别区域，检查是否有窗口【在目标之上】覆盖它
· OCR/视觉结果中，落在"被覆盖区域"的词一律丢弃
· 首选解法：让目标窗口真的成为前台（focus_window 修好之后）
· 次选解法：把目标窗口移到自己窗口不覆盖的地方
```

## 定位器链（按可靠性排序）

```
① 缓存      上次成功的定位（模板 / 相对坐标 / UIA Id）   命中即零成本
② UIA       元素身份（AutomationId + Rect）             非游戏；抗 DPI
③ ROI 模板  先裁剪再匹配                                 1px 级
④ OCR 词框  必须【合并相邻词成短语】+ 容忍形近字（结构匹配）
⑤ 几何      等距列 / 行距 / 锚点相对位置
⑥ Set-of-Marks  模型只选编号（附每框局部语义）
⑦ 裸坐标    仅人工确认后入库
★ 失败换【定位器】，不是换坐标 ★
```

## ROI 分层（比换模型更值钱）

```
· 永远不要对全屏做识别
· ROI 要"跟着内容走"：先用【锚点文字】定位，再裁它附近
· 不要用"屏幕百分比"当 ROI（实测全错）
· 滚轮操作 = 先把光标移到目标容器内，再滚那里
· 内层可滚动容器（chips 那种）必须单独识别出来
```

## 验证协议（可执行版）

```
① 局部 ROI 帧比对（全屏噪声大）          → "界面变了没有"
② 目标出现 / 消失                       → "我期待的副作用发生了没有"
③ OCR 复核关键文本（容忍全角逗号、千分位）→ "值对不对"
④ 离散答案核对：裁那一格 → 单独确认      → "是不是指对了对象"
⑤ 光标/前台/窗口状态【回读】（不信返回值）→ "动作真的作用对了吗"
```

## 速度（这一晚最直观的教训）

```
· 子进程一律 WaitForExit，禁止 Start-Sleep 固定时长
· PowerShell 调用要"一次拿全"（每次 Add-Type 编译 ~1.5s）
· 循环里：滚 N 次再 OCR 一次，不要每滚一次就截屏
· 多步任务合并进一个进程，减少冷启动
```

# 第三部分：为什么"这么简单的任务"会花这么久

用户的指令是：**打开公招计算 → 点高级资深干员 → 点特种干员 → 下滑 → 点控场 → 下滑找到水月 → 鼠标移过去**

**它其实同时要求 6 件事**：

| # | 要求 | 框架现状 |
|---|---|---|
| 1 | **窗口身份**：目标窗口真的可见且在前台 | ✗ `focus_window` 假成功、`IsWindowVisible` 漏窗口、同名窗口分不清 |
| 2 | **遮挡**：截图里不能混进别的窗口 | ✗ 完全没有这个概念 |
| 3 | **内层滚动**：chips 是独立可滚动框 | ✗ 只知道"往哪滚"，不知道"滚哪个容器" |
| 4 | **折叠面板结构**：结果是按标签分组的 | ✗ 没有"先找锚点再定 ROI"的机制 |
| 5 | **小字识别**：卡片名 ~15px | ✗ OCR 读不出；视觉模型能读但会被遮挡污染 |
| 6 | **位置核对**：确认指对了那一张卡 | ✗ 我甚至先用错了判据（比对清单而非核对对象） |

**六项全缺 → 每前进一小步就要现修一个洞** → 所以"简单任务"变成了整晚。

**修复顺序建议**（按"能消除多少下游问题"排）：
```
1. 动作三件套（前提断言 + 执行 + 效果断言）—— 地基，消除"假成功"
2. focus_window 真置前台 + 回读校验     —— 它是所有键鼠输入的门
3. 遮挡模型（动态取自己窗口 + z 序）    —— 消除"识别到别人的字"
4. 锚点驱动的 ROI（禁止百分比猜）        —— 消除"裁错区域"
5. 定位器链 + 缓存                      —— 消除"换坐标硬试"
6. UIA 通道                            —— 非游戏应用一次到位
7. Set-of-Marks                        —— 游戏场景
```
