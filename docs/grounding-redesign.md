# 定位系统重设计：把"让模型猜坐标"换掉

> 依据：2026-10-02 一整天的**实测数据**（不是推测）。所有"✗/✓"都对应当天真实发生的事故或成功。

## 一、诊断：问题不在"模型太弱"，在"分工错了"

现在整条链路是：**截图 → 多模态模型 → 直接要 x,y 坐标 → 点** ✗

| 手段 | 实测表现 |
|---|---|
| 让**多模态模型给坐标** ✗ | 同一按钮每次差 **20~120px**，最多偏 **260px**；还会**谎报**（"两个槽位都已进驻" ← 实际空的；"滚了没变化" ← 实际滚了） |
| **模板匹配** ✓ | 命中 **1.000**（1px 级），390ms |
| **OCR 词级框** ✓ | 精确到词的像素框（Windows.Media.Ocr） |
| **OCR + 几何结构** ✓✓ | 算计算器 `33×88`：**视觉调用 0 次**，六次点击全中，一次成功 |

**结论**：让一个**概率模型**去干**回归**（估计连续坐标）的活，是用错了工具。
坐标这件事应该由**结构化信息**给：模板框 / OCR 词框 / 控件树 / 几何约束。
模型只该干它擅长的：**语义**（这是什么界面、该点什么名字的东西）。

## 二、目标架构

```
她的意图（"点确认"）
   ↓
【定位器链】按可靠性从高到低依次尝试，第一个成功即用
   ① template  已知模板          1px 级，毫秒级          ← 已有 match.exe ✓
   ② uia       UIAutomation 控件树  精确，非游戏应用最可靠   ← 新增
   ③ text      OCR 词框          精确到词，覆盖"有字的目标"  ← 已有 find_text ✓
   ④ geometry  几何/结构约束      网格/等距列/窗口矩形      ← 计算器那次验证 ✓
   ⑤ som       Set-of-Marks      模型只选编号，不产坐标     ← 新增（重点）
   ⑥ coord     裸坐标            最后手段，且**必须验证**   ← 只留作兜底
   ↓
【执行】Win32 注入（已有 ✓）
   ↓
【验证】像素帧比对 + 目标出现/消失 + OCR 复核   ← screen_diff 已有 ✓
   ↓
【固化】命中一次 → 存模板 / 存流程 → 下次直接走 ①
```

## 三、五条铁律（每条都对应当天的一次真实失败）

1. **视觉模型永不产出坐标** ✗
   它可以回答"这里有个叫『确认』的按钮"，但坐标必须由定位器给。
   （纠正：现在 `screen_look` 的提示词**还在教它写 `ACTION: clickz|900,400`** —— 虽然已加白名单拦掉裸坐标，但提示词本身也该改。）

2. **失败要换【定位器】，不是换坐标** ✗✓
   实测她 90% 的"点错"都是这条没做到：同一个按钮换三四个坐标硬点。
   正确做法：`click` 没生效 → 改 `find_text` → 再不行 `screen_look` 裁小图 → 再不行上报。
   （`screen_diff` 已经能客观回答"生效了没有"，这条现在**可执行**了。）

3. **每个动作之后必须验证** ✓
   `screen_diff|1` 是确定性的（几毫秒、免费、不会说谎）。
   实测视觉模型判断"变没变"两次都说错 —— **不许再用它做这件事**。

4. **成功即固化** ✓
   命中一次就 `make_template` 存下来、或者把这段序列存成 `flow`。
   同一个接口第二次遇到就该走快路径（毫秒级），不再调模型。

5. **不确定就说不确定** ✓
   定位器返回置信度；低于阈值 → **上报卡点**，而不是"挑一个最像的点下去"。
   （她的"认不准就标注"习惯是对的，应该推广到定位层。）

## 四、Set-of-Marks 具体怎么做（Node/Electron 最小可行路径）

**思路**：把"猜坐标"（回归）变成"选编号"（分类）—— 这是 OmniParser 那一路的核心。

```
① 收候选元素
   · OCR 词框（有文字的目标，最准）
   · 模板命中框（已知图标）
   · UIA 控件矩形（若可用）
   · （可选）连通域/色块，找"看起来像按钮"的矩形
② 去重、过滤（太小/太大/重叠）、按阅读顺序编号
③ 用 nativeImage 在截图上画红框 + 大号数字（不需要额外依赖 ✓）
④ 问模型："要点『确认』，选几号？只回一个数字。"
⑤ 模型回 "7" → 取 7 号框中心 → 点
⑥ 验证（同铁律 3）
```

**为什么这比现在的做法强**：
- 模型输出从"1920×1080 里的一个点"变成"20 个选项里的一个" —— **搜索空间缩小几个数量级**；
- 编号旁的框是**程序画的**，坐标天然精确；
- 模型就算选错，也是"选错了一个真实存在的元素"，而不是"点到一个空地方"。

**代价**：一次视觉调用（现在常常要"看→点→再看→再点"好几轮，反而更贵）。

## 五、优先级与取舍（单人项目，资源有限）

**优先做**：
1. **修正提示词**：视觉模型不再产出坐标（几行字，立刻生效）
2. **`screen_diff` 纳入强制验证流程**（已建好，只差叫她用）
3. **定位器链的框架**（把现有 template/text 包成统一接口 + 依次降级）
4. **UIA 通道**（对**非游戏**应用价值极高 —— 计算器/设置/浏览器/资源管理器全都适用）
5. **Set-of-Marks**（对**游戏**这类没有控件树的场景，这是最有可能的突破）

**暂不做**：
- 自己训检测模型（没数据、没算力）
- 端到端 CUA 模型（UI-TARS 这类要 GPU + 权重，且实时性差）
- 尝试让游戏暴露控件树（不可能）

## 七、★ 2026-10-02 实测定论（这一节推翻了本文档早期的几个判断）

### 结论一：**这个系统的头号病不是"定位不准"，是"假成功"** ⭐⭐

实测到的"报成功但没生效"清单（每一条都当场复核过）：

| 工具 | 它报的 | 实测事实 |
|---|---|---|
| `focus_window` | `OK … UNTOP done` | **前台窗口一个字都没变** ✗（回读 `GetForegroundWindow` 确认） |
| `key\|ctrl+f` | `true` | Ctrl+F 发给了**别的窗口** ✗ |
| `type\|数据目录` | `true` | 字打进了**我自己的输入框** ✗（截图可见） |
| `click` | `已点击 (x,y)` | 可能落在别的窗口/空地方 ✗ |
| `find_text\|X` | `找到/没找到` | **屏幕任何角落**出现 X 就算找到 ✗（含聊天记录）→ 假阳性 |
| 视觉模型 | "两个槽位都已进驻" | **两个都是空的** ✗ |
| `windows_list` | "坐标可直接用来 click" | **统统偏 1.25 倍** ✗（1394/1115=1.2500，四个数全中） |

**后果**：她**做错了却无从知道** ✗ —— 所有工具都说成功了。今天观察到的"她点错""她说没变""她卡住"，追根大半在这。

### 结论二：**"窗口在前台"是一切定位的前提** ⭐⭐

实测链条：
```
窗口没在前台（被别的窗口盖住）
  → 截图里是【遮挡者的像素】（被盖住的部分根本没被捕获）
  → OCR 老老实实读了遮挡者的文字
  → 我的"按目标窗口矩形过滤"把那些字【归给了目标窗口】
  → 于是拼出屏幕上并不存在的目标 ✗
```
**所以"遮挡"必须当一等公民处理** ✓ —— 不是"尽量"，是**前置条件** ✓。

### 结论三：**OCR 的定位是可靠的，识别是不可靠的**（分两件事看）

- ✅ **定位可靠**：实测在窗口真正置前的条件下，OCR 给出 `公招计算 @ (115,570)`，
  `move` 过去 + `click` → **帧差 12.41%** ✓ **URL 变成 `/recruitment`** ✓ **页面内容变成公招计算器** ✓
  —— **一次命中** ✓
- ❌ **识别不可靠**：形近字会错，且**不告诉你它不确定**：`钼铅→铝铅`、`格雷伊→格蕾伊`、`珊比→瑕比`（排班图 45 个名字错 4 个）
- ⚠️ **隐藏杀手**：窗口被遮挡时会把遮挡者的文字算到自己头上（见结论二）

**所以 OCR 能用，但必须被四条约束夹住** ✓：
① 窗口真在前台 ② 只在窗口矩形内找 ③ **相邻词合并成短语**（中文常被逐字切开）④ 事后验证

### 结论四：**视觉模型既不能当定位器，也不能当验证器**

- 定位：它给坐标实测偏 20~120px、最多 260px；调研数据 16.2%（零样本）vs SoM 73.0%
- 验证：它今天**两次谎报**（"都已进驻" ✗、"滚了没变化" ✗）→ 调研也把"让模型当验证器"列为**明确不值得做**
- **只留一个用途**：回答"这是什么界面 / 该点什么名字的东西"这类**语义**问题 ✓

## 八、★ 整合后的设计（定稿）

### 五条原则
1. **事实来自确定性通道，模型只做语义** —— 坐标只能来自 模板 / UIA / OCR / 几何，不能来自模型
2. **每个动作都必须有【前提断言 + 效果断言】** ⭐ —— 这是今天最值钱的一条（详见下）
3. **失败换定位器，不是换坐标** —— 她今天 90% 的"点错"都是换坐标硬试
4. **窗口身份优先于像素位置** —— UIA 的 AutomationId / 窗口句柄 比坐标天然稳
5. **成功即固化** —— 命中一次就存模板 / 流程 / 缓存，下次走快路径

### 动作的统一模板（原则 2 的落地）
```
执行前：断言前提
   · 目标窗口 == 前台窗口（回读 GetForegroundWindow，不信工具的返回值）
   · 目标元素存在（模板/文字/UIA 三者任一能证实）
   · 坐标落在目标窗口矩形内
执行：Win32 注入
执行后：断言效果
   · 局部 ROI 帧比对（全屏噪声大）
   · 目标出现/消失（点了"确认"→ 面板应该消失）
   · OCR 复核关键文本（URL / 标题 / 名字）
失败：换定位器重试 N 次 → **显式失败**（说清卡在哪一步、试过什么）
成功：写回缓存
```

### 定位器链（定稿顺序，来自调研修正）
```
① 缓存        上次成功的 selector / 模板 / 相对坐标     命中即零成本
② UIA 元素    Name + AutomationId + Rect               非游戏应用；游戏跳过
③ ROI 模板    先裁剪再匹配                             1px 级
④ OCR 词框    短语合并 + 窗口内过滤                     有文字的目标
⑤ 几何约束    等距列/行距/窗口矩形                      重复结构
⑥ Set-of-Marks 模型只选编号（**必须附每框局部语义**）    游戏等无控件树场景
⑦ 裸坐标      仅人工确认后入库                          兜底
```

## 九、★ 落地优先级（按"收益 ÷ 工作量"）

| 序 | 做什么 | 工作量 | 拦住今天的哪个事故 |
|---|---|---|---|
| **1** | **动作工具加"前提+效果断言"**（尤其 key/type/click 的前台断言） | 小 | ⭐ 今天**全部**的"点错/打错窗口" |
| **2** | **修 `focuswin`**：解锁 (`AttachThreadInput`/Alt) → SetForegroundWindow → `IsIconic→SW_RESTORE` → **回读校验，不成功就返回失败** | 小 | ⭐ 它是所有键鼠操作的**门** |
| **3** | 修 `windows_list` 的 **1.25× 坐标 bug** | 极小 | 按它给的坐标点必偏 |
| **4** | `find_text` **限定在指定窗口矩形内**，并支持短语合并 | 小 | 假阳性（拿别处的文字当目标） |
| **5** | `screen_diff` 加 **ROI 参数** | 小 | 验证不可用（全屏噪声大） |
| **6** | **定位器链框架 + 缓存层** | 中 | "换坐标硬试"这个模式 |
| **7** | **UIA→JSON 桥**（C# 侧） | 中 | 非游戏应用一次到位 |
| **8** | **Set-of-Marks** | 大 | 游戏场景 |

**1–5 都是小改动，且 1、2、3 直接对应今天最严重的三个发现** ✓。

## 十、明确不做

- ❌ 让模型直接给坐标
- ❌ 让模型当验证器
- ❌ 自训/微调 grounding 模型
- ❌ 上 SAM/SEEM 做通用分割标框（OCR 词框 + 模板 + 连通域已够）
- ❌ 全屏 1080p 直接送模型（高分屏 grounding 会崩）
- ❌ 用 `focus_window` / `key` / `type` 的**返回值**判断成败（必须回读）

## 附：调研结论（2026-10-02，已核实，含对本文档早期错误的更正）


### ⚠️ 更正：本文档初稿引用的一组数字是错配的
初稿写"直接要坐标约 18.9%、OmniParser 73.0%" —— **这两者不是同一基准，不能对比**。
- **18.9%** 出自 **ScreenSpot-Pro**（高分辨率专业场景），原文说的是"**现有最佳模型**仅 18.9%"
- **GPT-4V 零样本的真正基线**是 **ScreenSpot 16.2%**（桌面图标类仅 11.8%）
- OmniParser 的 **73.0%**（桌面图标 63.6%）是对着 16.2% 这个基线比的
来源：[OmniParser 论文 Table 2](https://arxiv.org/html/2408.00203v1)、[ScreenSpot-Pro](https://arxiv.org/abs/2504.07981)

### 关键量化（都来自上面两个来源）
| 做法 | 分数 | 备注 |
|---|---|---|
| GPT-4V 零样本直接要坐标 | 16.2% | 桌面图标 11.8% |
| GPT-4V 指认 SoM 编号 | 70.5% | **光画编号还不够** |
| ＋**每框附局部语义**（框内文字/图标功能） | **93.8%** | ★真正的关键在这一步★ |
| ScreenSeekeR（**级联裁剪缩小搜索区**，无训练） | 48.1% | ★"ROI 分层比换模型更值钱"★ |
| SeeClick / CogAgent（训练式坐标回归） | 53.4% / 47.4% | 不可靠的是**通用 VLM 零样本回归**，不是坐标本身 |

### 各通道的边界（核实过的坑）
| 通道 | 边界 / 坑 |
|---|---|
| **UIA** | 能拿 AutomationId/Name/ControlType/BoundingRectangle/Pattern。**Node 没有成熟绑定** → 复用我们已有的 **C# 侧**做 UIA→JSON 桥。跨 UIPI 需 `uiAccess=true` + **Authenticode 签名 + 装 Program Files**。游戏/自绘 UI **基本没有**（"UIA 只用于找窗口，之后截图+坐标"） |
| **Electron 应用** | Chromium 无障碍树嵌在原生宿主里，树深、含隐藏 webview；**默认只在检测到辅助技术时才开**，可 `app.setAccessibilitySupportEnabled(true)` 手动开 |
| **模板匹配** | Airtest 的顺序是 SURF→Template→BRISK→MultiScaleTemplate，阈值默认 0.7（建议 0.6~0.9）+ 自定义 `RESIZE_METHOD` 对齐游戏缩放。SikuliX 在缩放/DPI 变化后识图失败是常见问题。AutoHotkey ImageSearch **要求像素尺寸完全一致** → **我们的多尺度匹配已经比它强** |
| **候选去重** | OmniParser 合并 OCR 框与检测框、**>90% 重叠去重**（OCR/模板优先） |

### 混合架构的共同分工线（四个项目都一样）
[Power Automate 自愈](https://learn.microsoft.com/en-us/power-automate/desktop-flows/self-healing) / [workflow-use](https://github.com/browser-use/workflow-use) / [Skyvern code caching](https://www.skyvern.com/docs/developers/features/code-caching) / [UFO²](https://arxiv.org/abs/2504.14603)：

> **确定性通道先跑 → 只在"找不到/不确定"时叫一次模型 → 模型只输出【候选编号】或【修复后的 selector】，绝不输出坐标 → 成功即固化**

⭐ Power Automate 的自愈返回的是 **selector（元素身份）而不是坐标** —— 这正是"模型结果必须固化成确定性步骤"的标准做法。

### ★ 修正后的优先级（UIA 提到 OCR 之前，缓存放最前）
```
① 固化缓存   上次成功的 selector/模板/相对坐标 —— 命中即零成本
② UIA        元素身份（AutomationId/Name/Rect）—— 抗 DPI/缩放；游戏跳过
③ ROI 模板   先裁剪再匹配
④ OCR 词框 + 布局聚类
⑤ 几何/相对布局约束
⑥ Set-of-Marks（模型只选编号，且**必须附每框局部语义**）
⑦ 裸坐标     仅人工确认后入库
```

### ★ 验证协议（研究原话："别信模型自述 —— 谎报已生效就死在这"）
```
点击前：断言元素存在
点击后：**局部 ROI** 帧比对（全屏噪声大，我现在的 screen_diff 是全屏 —— 必须加 ROI）
      → 断言目标出现/消失
      → OCR 复核关键文本
      → 失败重试 N 次再**降级换定位器**
      → 成功路径**写回缓存**
顺序照抄 Power Automate：Retry → AI 兜底 → 显式失败
```

### 明确**不值得做**（资源有限，单人项目）
- ❌ 自训/微调 GUI grounding 模型
- ❌ 上 SAM/SEEM 做通用分割标框（重且慢；**OCR 词框 + 模板 + 连通域已经够**）
- ❌ 自研通用图标检测器（除非目标程序固定且量极大）
